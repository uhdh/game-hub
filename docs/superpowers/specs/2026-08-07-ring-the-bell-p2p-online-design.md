# 링 더 벨 — 온라인 2:2 P2P 대전 — 설계 문서

## 개요

기존 `ring-the-bell.html`은 사람 1명(index0, `players[0]`) + AI 3명을 **한 브라우저 안에서 전부 시뮬레이션**하는 4인 2팀 카드 게임이다. 이번 설계는 여기에 **"나 + 내 AI 팀원 : 상대 + 상대 AI 팀원"** 형태의 온라인 2:2 대전 모드를 새로 추가한다. 실시간 게임 데이터(카드 행동)는 WebRTC `RTCDataChannel`로 완전히 P2P로 오가고, 연결을 맺기 위한 시그널링(offer/answer/ICE candidate 교환)만 Supabase Realtime 채널을 우편함으로 빌려 쓴다.

기존 1인용 모드(AI 3명과 대전)는 **그대로 유지**하며, `?room=<code>` URL 파라미터 유무로 두 모드를 분기한다.

## 배경 조사 — 왜 핵심 로직을 일부 고쳐야 하는가

`ring-the-bell.html`의 게임 로직은 33번째 줄 단일 IIFE 안에 캡슐화돼 있어 `players`/`turn`/`deck` 같은 상태와 `take()`/`discardSelected()`/`showBell()` 같은 함수를 바깥에서 직접 참조할 수 없다. 지금까지의 모든 후속 패치(38번째 줄 이후, `HISTORY.md`에 기록된 다수의 수정 포함)는 이 제약 때문에 DOM 관찰(`MutationObserver`)이나 클릭 시뮬레이션으로만 게임에 개입해왔다.

온라인 2:2를 만들려면:
1. "나"의 좌석이 **항상 `players[0]`으로 고정**된 하드코딩(`turn!==0`, `players[0].hand` 등)을 `mySeat` 변수로 일반화해야 한다 — 초대받은 쪽 화면에서는 "나"가 `players[1]`이어야 하기 때문.
2. 다행히 팀 배치는 이미 우리가 원하는 순서와 일치한다: `index0=나(A팀)`, `index1=카이(B팀)`, `index2=루나(A팀 AI)`, `index3=미나(B팀 AI)`. 초대받은 사람이 그냥 "카이" 좌석을 대신 차지하면 되고, 배열 순서 자체를 바꿀 필요는 없다.
3. 원격 사람의 턴은 AI처럼 자동 진행하지 않고 네트워크로 받은 행동을 재현해야 하는데, `#deck`/`#discard`/`#hand .card`/`#bell` 각 DOM 요소에 이미 `onclick`이 직접 바인딩돼 있어(`el.click()`을 호출하면 실제 내부 로직이 그대로 실행됨) 이 클릭 시뮬레이션 트릭으로 내부 함수에 접근하지 않고도 원격 행동을 재현할 수 있다.

이번 작업은 **핵심 IIFE의 좌석 하드코딩만 최소로 고치고**, 네트워크/방 관리/UI는 지금까지처럼 파일 뒤에 덧붙이는 스크립트 블록으로 처리한다. 게임 엔진 전체를 분리하는 리팩터는 하지 않는다 — 이미 검증된 1인용 로직의 회귀 위험을 최소화하기 위함이다.

## 신뢰 모델 — 대칭 시뮬레이션

두 클라이언트가 **동일한 시드로 동일한 계산을 독립적으로 수행**하는 방식을 쓴다(호스트가 전체 상태를 쥐고 게스트에게 필터링된 정보만 주는 "호스트 권위" 방식은 채택하지 않음).

- 양쪽 브라우저 모두 4인 전체 상태(손패 포함)를 로컬에 들고 있다. 이론상 개발자도구로 상대 손패를 들여다볼 수 있지만, 기존 1인용 모드도 이미 콘솔로 AI 손패를 볼 수 있는 구조라 새로 생기는 위험이 아니며, 캐주얼한 친구 대전 용도로는 허용 가능한 트레이드오프로 판단했다.
- 사람의 턴(자기 자신의 턴)만 상대에게 행동을 전송한다. AI 턴(양 팀의 AI 팀원)은 결정론적이므로 **전송하지 않고 양쪽이 각자 계산** — 데이터 채널 트래픽이 최소화된다.

## 셔플 결정론 수정 (버그 수정, 온라인/오프라인 공통 적용)

기존 `makeDeck()`은 `deck.sort(()=>Math.random()-.5)`로 섞는다. 이 방식은 **동일한 `Math.random()` 출력 시퀀스를 넣어도 브라우저 엔진에 따라 비교자 호출 순서가 달라질 수 있어 최종 순서가 어긋날 수 있다**(ECMAScript 스펙이 정렬 비교 호출 순서를 강제하지 않음). 두 클라이언트가 서로 다른 브라우저/엔진을 쓰면 덱 순서가 어긋나 게임이 깨질 실질적 위험이 있다.

- `sort` 기반 셔플을 **Fisher-Yates 셔플**로 교체한다. 어떤 JS 엔진에서도 동일한 입력 → 동일한 출력을 보장한다. 이 수정은 1인용 모드에도 자연스럽게 적용되며 부작용이 없다(순수 버그 수정).
- 온라인 모드에서만 `Math.random`을 **공유 시드 기반 PRNG**(mulberry32 — 이 프로젝트에서 과거 결정론적 테스트에 이미 써본 이력이 있음, `HISTORY.md` 2026-08-04 항목 참고)로 교체한다. 시드는 방 생성 시 호스트가 만들어 시그널링 단계에서 게스트에게 1회 전달.
- 1인용 모드는 시드 교체 없이 기존 `Math.random` 그대로 사용(회귀 없음).

## 네트워크 설계

### 시그널링 (연결 수립 전용, Supabase Realtime)

1. 호스트가 "친구와 온라인 대전" → "방 만들기" 클릭 → 짧은 방 코드 생성 → `room:<code>` Realtime 채널 구독 → `RTCPeerConnection` 생성(공용 STUN 서버만 사용, TURN 없음 — 이번 범위 제외) → `offer` 생성 → 채널로 broadcast → `ring-the-bell.html?room=<code>` 링크를 화면에 표시(복사 버튼).
2. 게스트가 그 링크로 접속 → 같은 채널 구독 → offer 수신 → `RTCPeerConnection` 생성 → `answer` 생성 후 broadcast.
3. 이후 발생하는 ICE candidate는 trickle 방식으로 같은 채널을 통해 계속 교환.
4. DataChannel이 열리면 시그널링 채널은 목적을 다했으므로 구독 해제.

### 게임 프로토콜 (DataChannel, P2P)

연결 직후 호스트가 `init` 메시지(공유 PRNG 시드 + 현재 수신호 기준 점수값) 1회 전송 → 양쪽이 동일한 시드로 `startSet()` 실행. 이후 오가는 메시지는 두 종류뿐:

- `action` — 자기 턴에 한 행동 하나: `draw-back` / `draw-front` / `discard:<idx>` / `bell`. 수신 측은 대응하는 DOM 요소에 `.click()`을 호출해 재현한다(위 "배경 조사" 항목의 클릭 시뮬레이션 트릭).
- `checksum` — 세트 종료 시점(`advance()` 호출 시점)마다 각자 `players.map(p=>p.hand)` 기반 짧은 체크섬을 계산해 교환. 값이 다르면 "동기화 오류가 발생했습니다. 게임을 다시 시작해주세요" 안내만 띄운다 — 복구 로직은 만들지 않고 감지만 한다.

### 연결 끊김 처리

재연결/이어하기 로직은 만들지 않는다. DataChannel이 끊기면 "상대와의 연결이 끊어졌습니다" 안내와 함께 홈으로 이동하는 버튼만 제공한다(STUN-only로 애초에 연결 실패 가능성을 감수하기로 한 결정과 같은 선상).

## UI / 진입 흐름

- `#rulesBtn` 옆에 "친구와 온라인 대전" 버튼을 추가.
- 클릭 시 기존 `#modal` 오버레이를 재사용해 "방 만들기" / "참가하기(링크로 접속)" 갈림길을 보여준다.
- **방 만들기**: 방 코드 생성 → 초대 링크 표시 + 복사 버튼 → "상대 접속 대기 중…" 표시 → 게스트 접속되면 자동으로 `startSet()` 진행.
- **참가하기**: `?room=<code>` 파라미터로 페이지 진입 시 이 갈림길 모달을 건너뛰고 곧장 "접속 중…" 상태로 시작.
- URL에 `room` 파라미터가 없으면 지금처럼 그냥 1인용 모드로 시작 — 파라미터 유무가 모드 분기 기준.
- 온라인 모드 진행 중에는 화면 상단에 상대 닉네임 + 연결 상태(연결됨/끊김) 표시만 추가. 새 CSS 컴포넌트는 최소화하고 기존 스타일을 재사용한다.

## 팀/좌석 매핑

| index | 이름 | 팀 | 온라인 모드에서의 정체 |
|---|---|---|---|
| 0 | 나 | A | 호스트(방 만든 사람) |
| 1 | 카이 → 게스트 닉네임으로 표시 | B | 게스트(초대받은 사람) |
| 2 | 루나 | A | 호스트의 AI 팀원 (결정론적, 양쪽이 각자 계산) |
| 3 | 미나 | B | 게스트의 AI 팀원 (결정론적, 양쪽이 각자 계산) |

턴 순서는 기존 배열 순서(0→1→2→3) 그대로 유지 — 결과적으로 "사람→사람→AI→AI" 순서가 된다.

## 이번 범위에서 명시적으로 제외하는 것

- TURN 서버 (STUN만 사용, 연결 실패 시 안내만 하고 재시도 로직 없음)
- 랜덤 매칭/로비 (초대 링크 전용, 자동 매칭은 별도 기회에)
- 재연결/이어하기 (끊기면 새로 시작해야 함)
- 관전 모드, 게임 중 채팅
- 히든 정보의 암호학적 보호 (대칭 시뮬레이션 방식 채택에 따른 트레이드오프로 이미 합의됨)

## 테스트 방침

핵심 로직 변경 중 회귀 위험이 가장 큰 지점은 (1) Fisher-Yates 셔플 교체, (2) `mySeat` 일반화다. 구현 단계에서 각각에 대해 최소 하나의 결정론적 확인(시드 고정 후 셔플 결과가 항상 동일한지, `mySeat=0`일 때 기존 1인용 동작이 그대로인지)을 남긴다.
